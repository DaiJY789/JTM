# 虚假信息检测系统工程化评估与规划

本文档基于当前仓库状态整理，用于把现有 demo 演进为更完整、可评测、可扩展、可运维的虚假信息检测系统。

## 1. 当前系统概况

当前系统是一个 FastAPI 单体应用，前端为静态页面，后端提供统一 `/detect` 和 `/followup` 接口。

已具备能力：

- 文本检测：声明抽取、证据检索、文本判定、用户可读解释。
- 图像检测：图像三分类、局部伪造类型、可疑区域、取证工具链、视觉大模型综合判断。
- 多模态检测：文本检测、图像检测、图文一致性检测并行执行，再进行融合判定。
- 网页输入：支持 `webpage_url`，抽取网页正文和代表图，复用多模态检测流程。
- 会话管理：本地持久化对话、上传图、最新输入和结果，支持恢复、追问、删除。
- 工具体系：已有 SRM、噪声、复制移动、CFA、频域、人脸生物学、ROI、增强等图像工具。
- 测试基础：已有文本、图像、多模态、网页抽取、schema、会话等单元测试。

当前定位仍偏 demo：功能可串联，但缺少系统性评测、任务边界、质量门禁、可观测性和生产级稳定性设计。

## 2. 主要不足

### 2.1 产品与任务边界不足

- 检测任务定义还不够稳定。文本事实核查、图像真实性、图文一致性、网页级多模态真实性被放在同一个入口，但缺少统一任务协议和输出解释标准。
- 标签体系混杂。文本有真假/谣言标签，图像有真实/伪造/合成，多模态有单模态异常和图文一致性标签，前端展示依赖映射，长期会变得难维护。
- 网页级检测目前只使用代表图，无法覆盖一个网页内多图、多视频、多段引用、图注和正文之间的复杂关系。
- 用户问题和检测模式耦合较弱。当前 `auto` 主要依据是否有文本/图片判断，不能充分理解用户指定的检测重点。

### 2.2 数据流与架构边界不足

- `/detect` 承担输入解析、网页抽取、会话保存、调用编排和响应包装，职责偏重。
- 网页抽取、图像下载、图片保存、检测编排之间还没有标准化的 `InputArtifact` 或 `EvidenceBundle` 数据结构。
- 多模态检测只支持单图。网页和新闻场景需要多图、多图注、多段文本的结构化输入。
- 当前并发使用 `ThreadPoolExecutor`，适合 demo，但缺少统一超时、取消、重试、资源隔离和任务状态管理。
- 文件输出集中在本地目录，缺少 artifact 生命周期管理、清理策略和访问权限控制。

### 2.3 模型可靠性不足

- Prompt 是核心控制面，但缺少版本管理、回归集和 prompt 变更评测。
- 模型输出虽然有 JSON 解析和归一化，但仍可能出现字段缺失、理由与标签不一致、过度自信等问题。
- 图像检测容易在“工具分数”和“视觉观察”之间摇摆。近期已强化视觉判断，但仍需要数据集验证。
- 文本检测依赖搜索结果和 LLM 判断，缺少证据可信度建模、来源评级、时间一致性校验。
- 多模态融合策略主要是规则 + LLM 解释，缺少可量化的冲突分级和置信度校准。

### 2.4 工具链不足

- 图像工具多为启发式工具，覆盖局部噪声、频域、复制移动等，但对语义编辑、文字重绘、上下文错配、截图二次传播等现实场景覆盖不足。
- 外部深度模型 TruFor、CAT-Net、DIRE 目前默认不启用，缺少标准适配层和模型服务化部署方案。
- C2PA 暂停使用，来源凭证能力缺失。
- 工具调用策略仍由 prompt 和简单规则控制，缺少基于图像内容的可学习或可配置 tool router。
- 工具结果没有统一证据强度等级，前端和融合逻辑难以稳定解释。

### 2.5 网页级检测不足

- 当前网页抽取只解析 HTML，不能处理动态渲染页面、登录页面、反爬页面、视频内容、嵌入帖文。
- 只取代表图进入检测，不会逐图分析，也不会把正文段落、图片、图注按位置关系建模。
- 没有 URL 安全策略，例如内网地址阻断、重定向审计、下载文件类型约束、域名黑白名单。
- 没有网页快照能力，检测结果无法复现当时页面状态。
- 没有网页来源可信度、发布时间、作者、站点元数据、引用链等结构化抽取。

### 2.6 评测体系不足

- 当前测试主要是单元和 schema 测试，缺少真实样本回归集。
- 没有统一指标：准确率、召回率、误报率、漏报率、图文一致性 F1、区域定位 IoU、解释质量评分等。
- 没有区分场景集：新闻文本、社媒截图、AI 生成图、局部重绘、图文错配、旧图新用、讽刺/梗图、网页多图。
- 没有成本和时延基准。多模型调用和网页抽取会显著影响响应时间。
- 没有人工标注闭环，无法持续修正错误样例。

### 2.7 前端与用户体验不足

- 前端是单页静态 UI，适合 demo，但缺少任务流清晰分区。例如网页检测、图文检测、单图检测在同一输入区里容易混淆。
- 网页输入抽取出的文本和代表图已能回填，但候选图片列表、网页元数据、图文对应关系还未可视化。
- 检测结果缺少证据视图分层：最终结论、关键证据、工具证据、模型推理、限制条件、原始 JSON 应分层展示。
- 可疑区域只支持单图 overlay，多图网页场景还没有展示方案。
- 对失败状态、部分成功、工具超时、证据不足的解释还不够明确。

### 2.8 运维与安全不足

- 配置中仍存在默认密钥样式的字段，生产化必须迁移到环境变量或密钥管理。
- 缺少结构化日志、请求 ID、链路追踪、模型调用耗时、工具耗时、错误分类统计。
- 没有队列和异步任务机制，长任务会占用请求连接。
- 缺少限流、鉴权、配额和成本保护。
- 网页抓取存在 SSRF、超大响应、恶意 HTML、重定向到内网等安全风险，需要系统性防护。
- 本地会话和 artifact 没有明确清理周期，长期运行会积累存储。

## 3. 建设目标

建议将系统目标拆成四层：

1. 可用 demo：支持文本、图片、图文、网页输入，能返回结构化结论和可读解释。
2. 可评测系统：每次模型、prompt、工具变更都能在固定样本集上回归。
3. 可扩展平台：输入、证据、工具、模型、融合、展示解耦，支持多图和网页结构化分析。
4. 可运行服务：有安全、监控、队列、成本控制、数据管理和部署规范。

## 4. 目标架构

建议引入以下核心抽象：

### 4.1 输入层

- `InputArtifact`
  - `type`: text, image, webpage, video, screenshot
  - `source_url`
  - `local_path`
  - `content`
  - `metadata`

- `WebpageSnapshot`
  - `url`
  - `final_url`
  - `title`
  - `text_blocks`
  - `images`
  - `captions`
  - `published_at`
  - `author`
  - `site_name`
  - `html_snapshot_path`

### 4.2 分析层

- 文本声明抽取器
- 网页结构抽取器
- 图像真实性分析器
- 图文对齐分析器
- 来源可信度分析器
- 工具调度器
- 证据检索器

### 4.3 融合层

- `EvidenceBundle`: 统一承载文本证据、图像证据、网页证据、工具证据。
- `VerdictFusion`: 将多路证据映射到统一输出协议。
- `ConfidenceCalibrator`: 对模型置信度、工具证据、检索证据进行校准。

### 4.4 展示层

- 最终结论
- 关键证据摘要
- 文本声明与证据表
- 图片/多图可疑区域
- 图文一致性矩阵
- 网页抽取内容和候选图片
- 限制条件与复核建议

## 5. 分阶段规划

### 阶段 0：稳定当前 demo

目标：保证现有功能可运行、可演示、可回归。

任务：

- 清理启动说明和端口配置，避免系统端口冲突。
- 固化当前 `/detect`、`/followup`、网页输入、历史管理行为。
- 将 prompt 变更纳入测试，至少验证关键约束字符串和输出 schema。
- 增加 smoke test：文本、图片、图文、网页四类输入的最小链路。
- 清理默认密钥，完善 `.env.example`。

验收：

- `pytest tests` 通过。
- 前端四类输入都能提交并展示结果。
- 网页 URL 检测后能展示抽取正文和代表图。
- README 启动命令在本机可复现。

### 阶段 1：统一数据结构和输出协议

目标：降低功能继续扩展时的耦合。

任务：

- 定义 `InputArtifact`、`EvidenceBundle`、`DetectionTask`、`DetectionReport`。
- 将 `/detect` 中的网页抽取、输入合并、会话保存拆出到服务层。
- 统一标签体系和前端展示映射。
- 将 `raw` 中调试字段分层为 `artifacts`、`debug`、`evidence_trace`。
- 为文本、图像、多模态、网页检测定义统一的结果契约。

验收：

- 新 schema 有单元测试。
- 现有前端不依赖不稳定 raw 字段展示核心信息。
- 各检测模式输出字段一致，缺失字段有明确默认值。

### 阶段 2：网页级多模态分析

目标：从“网页代表图检测”升级为“整页图文检测”。

任务：

- 网页抽取输出 `text_blocks`、`images`、`captions`、图片位置关系。
- 支持多图下载、缓存和逐图分析。
- 对每张图执行图像真实性检测。
- 对正文与每张图/图注做图文一致性检测。
- 生成网页级融合报告：正文可信度、图片真实性、图文错配、来源风险。
- 前端展示候选图片列表、逐图结论和图文对应关系。

验收：

- 一个网页可输出多图分析表。
- 支持至少 N 张图片上限，例如 5 张，避免成本失控。
- 网页检测结果能说明每张图对应的文本证据和风险。

### 阶段 3：评测与数据闭环

目标：每次修改都能量化影响。

任务：

- 建立样本集：
  - 文本事实核查样本
  - 真实图像样本
  - 合成图像样本
  - 局部伪造样本
  - 图文错配样本
  - 网页多图样本
- 定义评测脚本和指标。
- 保存模型输入、输出、工具结果和人工标签。
- 建立错误样例库，按错误类型分类。
- 增加 prompt 回归测试。

验收：

- 可以一键运行离线评测。
- 输出按版本保存评测报告。
- 任意 prompt 或工具策略变更必须附带评测结果。

### 阶段 4：模型与工具能力增强

目标：提升真实世界检测覆盖率。

任务：

- 接入可配置外部视觉模型服务，标准化 TruFor、CAT-Net、DIRE 等适配器。
- 恢复 C2PA/Content Credentials 检查，并明确其证据含义。
- 增加 OCR/画面文字检测，专门处理绶带、海报、截图文字、标牌篡改。
- 增加旧图新用/上下文错配检索：反向图片搜索、相似图检索、新闻时间线校验。
- 引入来源可信度模型：域名、作者、发布时间、引用链、历史可信度。
- 对图像工具输出做证据强度归一化。

验收：

- OCR 结果进入 `visual_analysis` 和图文一致性输入。
- 旧图新用样本集召回率有可量化提升。
- 外部工具不可用时不会影响基础流程。

### 阶段 5：服务化与运维

目标：支持长期运行和多人使用。

任务：

- 引入异步任务队列：网页和多图检测改为任务式接口。
- 增加请求 ID、结构化日志、耗时统计、模型调用统计。
- 增加限流、鉴权、配额和成本统计。
- 增加 artifact 清理策略。
- 对网页抓取加入 SSRF 防护、重定向审计、大小限制、MIME 校验。
- 提供 Dockerfile 和部署文档。

验收：

- 长任务不会阻塞 HTTP 请求。
- 能按请求追踪每个模型/工具调用耗时。
- 有基本安全策略和存储清理策略。

## 6. 优先级建议

近期优先级：

1. 建立评测样本和评测脚本。
2. 把网页检测从单代表图扩展到多图结构化分析。
3. 抽象输入和证据结构，降低 `/detect` 膨胀。
4. 增加 OCR/画面文字检测。
5. 加强日志、错误分类和耗时统计。

不建议优先做：

- 在没有评测集前继续大规模改 prompt。
- 在没有标准适配层前接多个外部模型。
- 在单请求同步架构上直接做无限多图网页检测。

## 8. 风险与决策点

- 是否面向生产服务：如果是，需要优先做安全、鉴权、限流、队列；如果只是研究 demo，则优先做评测和模型能力。
- 是否支持多图网页：支持后成本和时延会明显增加，需要任务队列和上限策略。
- 是否引入外部深度模型：需要明确模型部署、GPU 资源、输入输出规范和失败降级。
- 是否保存网页快照：可复现性会提升，但带来存储、版权和隐私问题。
- 是否接入用户反馈：能形成数据闭环，但需要标注协议和数据治理。

## 9. 最小可行下一版本

建议下一版本定义为：

- 支持文本、图片、图文、网页四类输入。
- 网页至少支持正文 + 多张图片抽取展示。
- 检测仍可先使用代表图，但结果中明确展示候选图片。
- 有 50 条固定回归样本。
- 有 `/healthz`、结构化日志和基础耗时统计。
- 所有核心 prompt 变更必须运行回归样本。

该版本的目标不是追求模型能力最大化，而是建立可持续迭代的工程基线。
